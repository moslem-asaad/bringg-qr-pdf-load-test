# BRNGG-57656 (S2.1) — `documents_ready` flexible webhook

Part of [BRNGG-55375](https://bringg.atlassian.net/browse/BRNGG-55375). Full rationale in [BRNGG-55375-QR-Code-Tech-Design.md](BRNGG-55375-QR-Code-Tech-Design.md) §3.

**Repo:** `hagmonia-js`. **Depends on:** nothing to build the webhook shape itself; wiring the live call depends on BRNGG-57148 (S4) reaching the point where it flips a document to `ready`. **Can be coded and tested independently** with a fixture document, then wired in last.

## ⚠️ Read first — the payload envelope is NOT settled (added 2026-08-21)

Everything below is real and buildable — the `documents` array item shape (`id`/`type`/`status`/`url`) is solid. **What isn't settled is what wraps that array.** The flexible-webhook "selectable entities" list has no `run` entity at all, and `documents` alone gives ADEO nothing to file against (their archive is order-keyed — a bare URL with no run identifier is a document they can't attach to a shipment). This is unresolved in the source ticket too (its own "Open before implementation" #1 and #2), and it's the live blocker behind a real customer commitment right now (`#adeo_efti` Slack, escalated to a sync 2026-08-21).

**Refined 2026-08-21, after deep research — don't mirror `run_ended.js`'s full shape.** `baseModel` doesn't determine payload shape (four `baseModel: 'run'` webhooks all produce different shapes) — the heaviness in `run_ended.js` comes specifically from it hand-calling `Run.serializeToWebhook`/`Task.serializeToWebhook` (~89 fields per task, ~100-500x more data than needed for a 10-20 stop route). Instead: **keep `baseModel: 'run'`, reach identifiers through the existing light `case 'run'` flexible-attribute path** (`base_webhook.js:349-367`, backed by `RunDataService`/`TaskDataService`). **Do not import or call `Run.serializeToWebhook` or `Task.serializeToWebhook`/`WebhookUtils.serializeTask` in this file** — those are the two functions that produce the field bloat, and neither is needed for what ADEO actually asked for.

**Option A vs. B — a question for Liel/ADEO, not a code decision, and the reason the exact payload still isn't final.** The source ticket only commits to *"at minimum a run identifier — **probably** also the order external IDs"* — whether run-only is enough depends on how ADEO's own archival system works (their archive is described as order-keyed), not on anything in this codebase.

**Option A — run only**, `fields: ['id', 'external_id']` on the `run` attribute, no `relations`:
```json
{ "run": { "id": 4821, "external_id": "ADEO-RT-4821" },
  "documents": [{ "id": 1, "type": "run_aggregation", "status": "ready", "url": "https://<host>/document/<token>" }] }
```
Risk: if ADEO files per shipment rather than per route, a bare route identifier doesn't say which of their orders this document covers.

**Option B — run + order identifiers**, adds `relations: [{name: 'tasks', fields: ['id', 'external_id']}]` on the `run` attribute — note `tasks` nests **inside `run`**, not as a sibling key, since it's `run`'s own relation:
```json
{ "run": { "id": 4821, "external_id": "ADEO-RT-4821",
           "tasks": [{ "id": 9001, "external_id": "ADEO-ORD-1001" }] },
  "documents": [{ "id": 1, "type": "run_aggregation", "status": "ready", "url": "https://<host>/document/<token>" }] }
```
Cost is marginal (still 2 fields/task, nowhere near the heavy path). Fallback if the relation config feels too implicit: a bespoke narrow `Task.query(...).fetchAll({columns: ['id', 'external_id']})`, mirroring `loading_ended.js:157-165`, owned entirely inside `documents_ready.js` the way `questionnaire_response_submitted.js` owns its own fetch.

Build the mechanism below regardless of which option wins — it doesn't change based on the answer, only the `relations` config does. But don't commit the exact envelope to anyone external until this is actually decided with Liel/Product.

## ⚠️ Delivery reliability — a real gap found here, separate from the envelope question (added 2026-08-22)

Deep research into how a webhook actually gets delivered once fired, since this is a compliance feature where ADEO expects exactly-once receipt.

**The full path — only the last hop does the actual HTTP POST, and that's outside this repo:**
```
your handler: createBackgroundEvent('documents.ready', merchantId, message)   [1: internal RabbitMQ queue, in-process]
  → WebhookApp.onWebhookEvent: looks up config, builds payload per URL         [2: still hagmonia-js]
    → sendWebHook → WebhooksService.send(...)                                 [3: publishes to Kafka topic 'webhooks'
                                                                                    (+ RabbitMQ during migration) —
                                                                                    the actual outbound POST happens
                                                                                    in a separate webhooks-service repo]
```
**hagmonia-js's involvement ends at the Kafka/Rabbit produce call succeeding.** Confirmed by reading `WebhooksService.send()` (`@bringg/service-utils`) directly — it never makes an HTTP request itself.

**No retry, no backoff, no dead-letter — inside this repo.** `sendWebHook` wraps everything in one try/catch that only logs on failure (`webhook_app.js:452-454`) — no requeue, no re-publish. Whether the downstream `webhooks-service` retries the actual HTTP delivery is **unverified** — that repo isn't in this workspace. Don't claim "exactly once" to ADEO without confirming that separately.

**No deduplication anywhere in the pipeline.** Every layer (event parsing, `sendWebHook`, `WebhooksService`) mints a fresh random UUID per call rather than deriving one from message content — there is no "already sent this for document X" check anywhere. **This means your handler's own idempotent-create guard (Phase 3) is the only thing preventing a duplicate delivery to ADEO** — there's no safety net at this layer to lean on instead. Fire this webhook exactly once per successful generation, deliberately, not as a side effect of something retryable.

**Confirmed safe no-op when nothing's configured** — directly tested in this codebase (`webhook_app_test.js:328-360`): no merchant config, or a blank URL, both skip cleanly with no error and no wasted work.

**🔴 Real observability gap, worth escalating rather than just noting.** There is no delivery-status table, no metric, and no query surface anywhere in hagmonia-js for "did merchant X actually receive their `documents_ready` webhook for run Y." The one thing that *could* correlate hagmonia-js's side to whatever the downstream service logs is `webhook_request_id` (generated fresh per send) — but whether `webhooks-service` actually persists/exposes anything keyed on it is unverified from here. **Before this ships, either (a) check `webhooks-service`'s own logging/metrics for delivery confirmation, or (b) add an explicit acknowledgment signal** (e.g. a status update on the `documents` row driven by a callback from `webhooks-service` once it confirms delivery) — otherwise a permanently-failed delivery to ADEO is invisible from Bringg's side until they notice the document never arrived.

**Two edge cases, each with a concrete answer:**
- **Merchant deletes/disables the subscription mid-flight** (between generation starting and finishing) — safe. Config is read fresh at fire-time via a cache-aside layer (LRU → Redis → DB) with write-time invalidation, never snapshotted earlier — a deleted subscription correctly results in the no-op path, not a stale send to a removed URL.
- **🔴 Read-after-write race: the webhook's own data-fetch for `documents` might not see the just-committed `upload_id`.** This is a genuine, currently-open risk, not a solved one — the `Document`/`DocumentDataService` classes this fetch would use don't exist yet (separate work stream, Phase 1), so this couldn't be fully verified end-to-end. The analogous already-shipped attributes (`case 'run':`) go through the same LRU/Redis cache-aside pattern config lookups use — if a `Document` write populates/reads that cache before the DB transaction commits, or bypasses the model's registered writing-service, the webhook's fetch could read a stale pre-`upload_id` copy even though the row is already correct. **Recommendation: don't re-fetch the document by ID for this webhook at all.** Pass the already-in-hand, freshly-written document object (the one your Phase 3 handler just updated) directly into the webhook's `message` payload, instead of letting `fetchWebhookData`'s `case 'documents':` re-fetch it through a cache-mediated DataService. If a fetch-by-id turns out to be unavoidable, whatever `Document` write-path gets built in Phase 1/3 needs to synchronously invalidate cache as part of the same commit — this is a requirement to carry into that work, not something fixable here alone.

## What's already there — the exact template to follow

`questionnaire_response_submitted.js` is a real, already-shipped webhook using this exact pattern (merchant selects which attributes it carries via `flexibleModelConfig()`). Copy its shape, not `run_ended.js` (which is intentionally thin and has no flexible-attribute mechanism).

- Webhook types are added by dropping a file in `app/services/webhooks/` extending `BaseWebhook`, registered in `app/services/webhooks/index.js` — no central enum, ~65 of these exist already.
- The flexible-attribute dispatch is `BaseWebhook.flexibleSerialize()` → `fetchWebhookData()` (a `switch` in `base_webhook.js`) → a per-attribute fetch.

## Steps

1. **`app/services/webhooks/documents_ready.js`** extending `BaseWebhook`, modeled directly on `questionnaire_response_submitted.js`.
2. **`flexibleModelConfig()`** on the new class for the `documents` attribute — `{name, allowedFields, defaultFields, allowedRelations, defaultRelations}` shape.
3. **New `case 'documents':`** branch in `fetchWebhookData` (`base_webhook.js`) + a small fetch producing:
   ```json
   { "id": 1, "type": "run_aggregation", "status": "ready", "url": "https://<host>/document/<token>" }
   ```
   **Must call the same derived-`status` method BRNGG-57146 defines** (`pending`/`ready`/`failed` from `upload_id`/`failed_at`) — do not recompute this independently. This is the one thing that keeps this payload and S6's driver-app payload provably identical.
4. **Register** in `app/services/webhooks/index.js`.
5. **Absent-not-empty semantics** — when `documents` isn't selected as webhook data, or the entity has no document, the key is absent, **never** an empty array (a consumer reads `[]` as "no document required," which is wrong).
6. **Wire the live trigger** — called synchronously from S4 (BRNGG-57148) right after a document's `upload_id` is successfully set, same process, no extra event/queue hop. **Pass the already-in-hand document object in the `message`, don't have `case 'documents':` re-fetch it by ID** — see the read-after-write race note above.

## Tests

- Payload shape parity test: for the same document, this webhook's payload and BRNGG-57150 (S6)'s driver-app payload must be byte-identical in shape.
- Unknown `type` values are ignored by consumers per the forward-compat requirement (`ecmr` will add a second type in 2027) — assert this doesn't error.
- Absent-vs-empty: confirmed absent (not `[]`) when there's no document, and confirmed absent when `documents` isn't selected as webhook data.
- No-config/blank-URL no-op: mirror `webhook_app_test.js:328-360`'s pattern — no error, no wasted fetch work.
- Delivery-boundary test: stub `WebhooksService.prototype.send` (the established boundary mock point, `webhook_app_test.js:1204`) and assert the exact payload/headers/merchantId passed to it — this repo's tests never go further than this boundary, and neither should this one.

## Acceptance criteria

1. On a run whose config enables generation, a completed generation pass emits exactly one `documents_ready` webhook.
2. `documents` is selectable as webhook data on this webhook type, and the payload shape matches the contract above exactly.
3. Absent, not empty, when there's no document or the attribute isn't selected.
4. Payload's `status` comes from the same derivation S2/S6 use — not recomputed independently.
5. **Before enabling for any real merchant:** the delivery-observability gap above is resolved one way or the other (either `webhooks-service`'s own confirmation is verified to exist, or an explicit acknowledgment signal is added) — not a code AC for this ticket alone, but a release gate for the feature.
